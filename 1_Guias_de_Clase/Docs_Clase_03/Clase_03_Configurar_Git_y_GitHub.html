Configurar Git y GitHub

Git es el cuaderno de versiones de su trabajo: guarda cada cambio y le permite volver atrás. GitHub es donde ese cuaderno vive en internet. Su agente necesita las dos cosas para traerse un proyecto, modificarlo y devolverlo. Este anexo es el registro de cómo quedó configurado en el equipo del docente.
Para qué le sirve a usted: no es para volverse programador. Es para que cuando le diga a Claude «tráete ese proyecto y arréglalo», el agente tenga con qué. Sin git, el agente ve archivos sueltos; con git, ve la historia completa y puede deshacer.
1

Instalar las tres piezas

Git, Git LFS y la herramienta de GitHub
Uno por uno, no los dos juntos 
winget install --id Git.Git -e --source winget
winget install --id GitHub.cli -e --source winget
PiezaPara qué es
gitEl control de versiones. Lo esencial
git-lfsPara repositorios con archivos pesados (modelos, videos, datos). Viene incluido con git
ghManejar GitHub desde la terminal: crear repos, ver issues, subir cambios
Dos trampas que le van a pasar:
  • winget solo acepta un programa por comando. Si pega el comando y le deja atrás cualquier cosa —hasta un comentario— lo toma como un segundo programa y falla. Pegue la línea sola.
  • Git pide permiso de administrador. Sale la ventana azul de Windows. Hay que darle aceptar usted mismo; si lo lanza un proceso automático, se queda esperando para siempre.
2

Cerrar la terminal y abrir otra

El paso que todo el mundo se salta

Apenas termina de instalar, escribe git --version en la terminal que tenía abierta y le dice «no se reconoce». Y entonces uno cree que la instalación falló.

No falló. Windows le entrega a cada programa la lista de rutas en el momento en que arranca. Su terminal arrancó antes de que git existiera, así que sigue con la lista vieja. Ciérrela y abra una nueva.

Regla general: instaló algo y «no se reconoce» → terminal nueva antes de buscar cualquier otra explicación. Aplica a git, a Python, a todo.
3

Decirle a git quién es usted

Sin esto, sus cambios quedan sin firma

Cada cambio que guarde queda firmado con un nombre y un correo. Si no los configura, git se niega a guardar o guarda sin autor.

Cambie el nombre y el correo por los suyos 
git config --global user.name  "Su Nombre Completo"
git config --global user.email "SU_ID+SU_USUARIO@users.noreply.github.com"

git config --global init.defaultBranch main
git config --global core.autocrlf true
git config --global core.longpaths true
git config --global credential.helper manager
¿Por qué un correo raro con noreply? Porque el historial de un repositorio es público apenas alguien lo copie, y su correo real quedaría ahí en texto plano para siempre. GitHub le regala una dirección de reenvío: le atribuye los cambios a su perfil igual —con foto y todo— pero sin exponer su correo. La encuentra en GitHub, en Settings → Emails.
AjusteQué evita
core.longpaths Windows corta las rutas a 260 caracteres. Sin esto, copiar proyectos con carpetas profundas falla con errores incomprensibles
core.autocrlf Windows y Linux marcan el fin de línea distinto. Sin esto, un archivo parece «cambiado entero» sin que usted tocara nada
credential.helper Que le pida la clave una sola vez y no en cada envío
4

La llave de GitHub

Y dónde NO ponerla

GitHub ya no acepta su contraseña desde la terminal. Se usa un token, que es una clave larga con permisos limitados. Se crea en Settings → Developer settings → Personal access tokens, tipo fine-grained.

Ese token va al archivo .env, igual que el de Hugging Face:

# C:\1_Automatic_Workflows\.env
GITHUB_TOKEN=github_pat_xxxxxxxxxxxx

La herramienta gh lo lee sola del entorno. Por eso no se corrió gh auth login: ese comando guardaría una segunda copia del token en otra carpeta, y la regla es una sola copia.

Nunca meta el token dentro de la dirección del repositorio. Es decir, nada de https://token@github.com/.... Funciona, sí — y por eso la gente lo hace. Pero queda escrito en texto plano dentro de la carpeta del proyecto y en el historial de la terminal. Copie la dirección normal y deje que Windows le pida la clave la primera vez.
Traerse un proyecto 
git clone https://github.com/USUARIO/NOMBRE_DEL_REPO.git
5

Comprobar que quedó bien

Cuatro líneas
En una terminal NUEVA 
git --version
git config --global user.email
gh api user --jq '.login'
gh repo list --limit 5

Si las cuatro responden, está listo. Si gh se queja de autenticación, es que el .env no está cargado en esa terminal.

Detalle técnico, por si automatiza la comprobación: para saber si gh está autenticado hay que mirar su código de salida, no el texto que imprime. gh escribe ese mensaje por el canal de errores, y PowerShell trata ese canal como si algo hubiera fallado — así que revisar el texto le haría ver como error algo que está perfecto.
6

Cuidar el token

Lo que aplica igual al de Hugging Face

Un token es una llave de su casa. Dos preguntas antes de crearlo:

  • ¿Cuándo caduca? Si le pone «sin caducidad», una fuga le sirve al que la encuentre para siempre. Póngale fecha — hasta un año.
  • ¿A qué alcanza? Un token fine-grained se puede limitar a repositorios concretos. Si lo deja abierto a toda la cuenta, pierde la ventaja de ser «fino».
Si el token se le escapa —lo pegó en un chat, en un correo, o quedó dentro de un archivo que subió— revóquelo y cree otro. Borrar el mensaje no sirve: ya quedó registrado en algún lado. Rotar toma treinta segundos; una cuenta comprometida, no.

La idea de fondo: git no es una herramienta de programadores, es una herramienta de versiones. El mismo problema que usted resuelve con «Propuesta_v2_FINAL_ahora_sí.docx», git lo resuelve bien: cada cambio queda firmado, fechado y se puede deshacer. Que el agente tenga acceso a eso es lo que le permite trabajar sin que usted pierda nada.
